# Wave 3 retro — frictions in the coordinator/sub-agent loop

Written mid-wave on 2026-08-30 from `beyond10x/harness`, wave 3: four units, four implementors,
three adversaries, seven correction rounds so far. Uncommitted; nothing here has been applied to the
skill.

Every item below is a thing that happened in this session, not a thing that could happen. Where a
number appears it was read from a command or an agent's report.

---

## 1. The skill on disk changed under a running session, silently

The copy of `wave/SKILL.md` loaded into the coordinator's context at invocation had **no** commit-
authorisation section. The copy on disk at `SKILL.md:168-192` requires stage 1 to report "one line
naming the commits approval authorises" and states "An operator who did not know they were granting
commit rights did not grant them."

The coordinator only discovered the difference because the operator asked what the skill said and it
went and `grep`ped the file. `/reload-skills` reported "no changes" and did not re-inject anything.

**Consequence:** the wave halted at the merge boundary, mid-flight, after one coordinator commit and
four implementor commits had already been made.

**Adjustment.** A skill has no version the session can quote. Either stamp `SKILL.md` with a version
or hash the frontmatter carries, and have the coordinator print it in the stage-1 report — so a
mismatch is visible in the transcript — or make `/reload-skills` state which files changed rather
than "no changes" when a loaded skill's bytes differ from disk.

## 2. The one mandatory stage-1 line is buried in a prose list

`SKILL.md:171-175` names five things the stage-1 report must carry, in one sentence, with the
load-bearing one last. It is the only one whose omission invalidates the whole approval.

**Adjustment.** Give stage 1 a literal template with the commits line as its own block, not a clause
in a sentence. A checklist item that is a sentence fragment inside a longer sentence is the one that
gets dropped.

## 3. The coordinator's own opening commit is never gated

Pre-flight (`SKILL.md:208-224`) checks the tree is clean, no worktrees survive, disk, cache, one
measured build, and the repository's agent file. It checks the base gate **before** the coordinator
writes anything.

Wave 3's opening commit `5641770` added `docs/plans/2026-08-30-wave-3.md`, which carried
`/home/operator` in two evidence cells. `scripts/check-no-home-paths.py` judges the index as well as the
worktree, so the integration branch was red from the wave's first commit. **Three separate
implementors reported it independently** — U1, U2 and U4 each spent report space on it — and none
could fix it, since it was not their file.

**Adjustment.** Add a pre-flight step *after* the opening store commit: run the cheap gate steps
(everything but `cargo test` and `clippy`) on the integration branch before the first worktree is
created. In this case that is four seconds and would have saved three agents' attention.

## 4. A unit that needs a shared file has no way to ask for one

The plan declared U2 (`crates/harness-cli/src/contract.rs`, `scripts/check-cli-contract.py`) and U4
(`crates/harness-tools`, `crates/harness-substrate`, `scripts/gate.sh`) file-disjoint. `scripts/gate.sh`
was assigned to U4 **by name** in both dispatch prompts.

U2 then legitimately needed a gate step for the self-test its own finding required, and edited
`scripts/gate.sh` and `AGENTS.md` anyway. Both edits turned out to be correct — its adversary
confirmed the ordering — and they merged cleanly only because the hunks were 6 lines apart.

The skill gives the coordinator the shared files and forbids implementors to touch them. It gives an
implementor no channel to say *I need one*, so the only options it has are to violate the assignment
or to leave the work undone.

**Adjustment.** Name the third option in the implementor's charter: return the exact patch for a file
it does not own, in its report, and do not apply it. The coordinator already does this for
`CHANGELOG.md` and `STATUS.md`; it is the same move and it should be the same rule.

## 5. Sub-agents cannot see each other, so they rediscover the same facts

Three implementors independently found and reported the home-path defect (§3). Two adversaries
independently established the same facts about substrate's `validate_root_name` widening. Two agents
independently hit the `git diff A..B` vs `A...B` problem when the integration branch advanced under
them.

**Adjustment.** The coordinator maintains one short "known and handled" note and pastes it into every
dispatch and every correction round. Three lines is enough: what is already reported, what the
coordinator owns, and the current integration-branch tip. This is cheap and it is the only shared
state the fan-out has.

## 6. Findings are relayed as the coordinator's prose, and the coordinator gets them wrong

Routing U3's second finding, the coordinator restated an adversary's mechanism in its own words and
got one step wrong: it claimed `workspace_root_identity` would fire `path_escape` at substrate
`0.2.1`. The implementor checked and it does not — the strict predicate sits behind
`create_workspace` and `workspace_fd`, neither of which an adopt calls. The conclusion survived (a
`0.2.1` rollback does break, at the first *write*, not the adopt) but only because the implementor
was told to verify rather than take it on the coordinator's word.

**Adjustment.** Two rules in the routing section: relay a finding's **measurements verbatim** with
the agent that made them attributed, and mark separately anything the coordinator concluded rather
than read. The instruction "verify this yourself, do not take it on my word" should be in the
template, not left to the coordinator to remember — it is what saved this one.

## 7. The adversary's write permission is underspecified, and the coordinator widened it

The charter says the adversary "writes failing test cases … never edits the implementation". In
practice an adversary must sometimes mutate the implementation to prove a guard is dead — that is
how U2's vacuous `readme.contains("short")` hatch and U4's four surviving mutants were established,
and those were the most valuable findings in the wave.

Having no rule for it, the coordinator invented one in the dispatch prompt: "scratch mutations are
fine if you restore them and say so." Results: every adversary restored correctly and proved it with
`git status --porcelain`; one left a `.pyc` in the worktree; one wrote to `/tmp`, against a standing
global rule, and self-corrected.

**Adjustment.** Make it a charter clause rather than a per-coordinator invention. Mutation-to-probe
is **permitted**, and the report must carry `git diff --stat` and `git status --porcelain` as proof
of restoration. The operator asked about exactly this behaviour during the wave and was right to —
it looks wrong and is currently justified nowhere a reader can find it.

## 8. Scratch files have no home, so cleanup is done by reading prose

Agents wrote scratch under `~/.cache/harness-wave3/` with no convention. One left a **579 MB**
`target/rollback-probe` from a detached-tree rollback probe; the coordinator only found it because
that agent listed it in its report and flagged the size. Others left `.orig` backups inside assigned
build directories, mutant fixtures in a sibling directory, and 60 log files in the wave root.

The skill's cleanup step (`SKILL.md:376-410`) covers worktrees, build directories and branches. It
does not cover scratch, and scratch is the part `git` cannot see.

**Adjustment.** Assign each agent a scratch directory the same way a build directory is assigned, and
record the triple (worktree, build dir, scratch dir) instead of the pair. Then cleanup is a loop, not
a reading exercise.

## 9. The two-pass attack budget does not say who verifies the last correction

`SKILL.md` bounds attacking at two passes and says to hand over to a person after that. It does not
say what happens to the **correction** that answers the second pass — which is, by construction, code
nobody has attacked.

Wave 3 hit this on all three attacked units. The coordinator invented "one more correction, no more
attacks, and I verify it myself", and did verify U4's re-pinned unit test by reading the diff before
merging. That is a reasonable rule and it is nowhere in the skill.

Evidence that this matters: every correction round found new defects. U2's passes returned 4 then 9
findings; U4's returned 3 then 4, and its final round fixed a model-facing defect in `tools.rs` that
predated the wave. There is no sign of convergence, which is the argument for a budget — but the
budget currently ends in an unverified state rather than a verified one.

**Adjustment.** State it: after the second pass, the correction that answers it is verified by the
**coordinator**, reading the diff, and the unit merges or goes to a person. Name what the coordinator
must check — that no assertion was dropped, that a re-pinned test is not a relaxed one.

## 10. Reports are excellent and enormous, which serialises the coordinator

Implementor and adversary reports in this wave ran to several thousand tokens each, in prose, with
the verdict scattered. They are unusually good — measured counts, exit statuses per command, honest
"not done" tables — and reading them is the coordinator's whole job for minutes at a time. The skill
warns against serialising the pipeline and then produces the thing that serialises it.

**Adjustment.** Require a fixed machine-readable header before the prose: verdict, files touched,
per-command exit status, findings count, whether anything outside the assignment was edited. The
coordinator can route on the header and read the prose only when routing needs it.

## 11. A coordinator-owed red case has no name

U2's adversary correctly wrote `the_status_page_names_the_argv_contract_version_this_build_pins`,
which asserts `STATUS.md` names the version the build pins. `STATUS.md` is the coordinator's file and
is written at close, so the case is **red in the unit's worktree by design** and goes green only
after the merge.

Every subsequent round had to carry "expect exactly one red and ignore it" as prose, and a reader of
the branch alone cannot tell that red from a real one.

**Adjustment.** Give it a name and a convention — a case that asserts a coordinator-owned file is
tagged as such in its own message, so the branch is self-describing. The alternative, forbidding
adversaries to assert coordinator files, is worse: this case is the only thing that would have caught
`STATUS.md` drifting.

## 12. A scoper's mechanism claim is treated like its surface claims

`story:interrupt-acked-before-a-turn-can-be-cancelled` carried a `## Scope` section marking lines
cited or inferred. Its surface claims were all correct. Its **mechanism** claim — "moving
`*active = Some(control)` above the `respond`/`notify` block closes it" — was wrong, and the
implementor measured it wrong: 5 red of 5 after making exactly that move. The real fix needed a
counter for interrupts arriving before the turn is dequeued at all, across two files the story never
named.

The cited/inferred distinction covers *where the work lands*. It does not cover *what would fix it*,
and a scope section that mixes the two invites an implementor to treat a guess as a plan.

**Adjustment.** The scoper's charter should either forbid mechanism claims or require them in a
separate, explicitly-labelled block — "hypothesis, unverified" — distinct from the surface section.

## Smaller things

- `protocol artifact new --summary "--substrate-embedded …"` fails clap parsing; `--summary=…` works.
  Worth a note in the planning skill, since summaries of CLI work routinely start with a flag.
- `git merge -F -` does not read stdin; it needs a real file. The branch-and-merge reference shows
  merge messages but not how to write one safely.
- Dispatch prompts should specify `git diff <base>...<head>` (three dots) always. Two agents were
  briefly confused when the integration branch advanced under their fork point, and one flagged it as
  a possible scope violation before working out it was not.
