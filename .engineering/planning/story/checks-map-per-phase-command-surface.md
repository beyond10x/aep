# Story: The development/checks map declares the commands each phase admits

## Outcome

A governed run under `drivers/development/checks.yaml` holds, in each `llm` step, the shell surface
that step's `commands:` declares and nothing wider: `specify` and `decompose` reach `aep plan artifact
…` only; `implement` reaches the repository's gate, generators and working-tree `cargo` verbs; no
step reaches a general shell. The rule is read out of the map, and a map that declares no
`commands:` on a step is held to the surface it is held to today.

## Context

`driven_surface` (`crates/edge/aep-cli/src/drive.rs`) holds every driven `llm` step to one simple
invocation of `aep plan artifact …` or `aep observe trace …`, plus the read-only programs, in every
state alike. The step map cannot say otherwise: `RawLlmStep` carries `scope:` for writes and nothing
for commands. Governed runs in ess-ui-templates and metaharness reported the gap, and the
orchestrator decided the per-phase surface on 2026-10-23 (approval-record
`checks-map-command-surface`). This story is that decision, filed and implemented.

## Acceptance

1. `RawLlmStep` accepts `commands:`, a list of argv prefixes; `LlmStep.commands` carries the
   validated list and is absent from the canonical form when empty, so an undeclared map's digest
   is unchanged; `schemas/generated/driver-steps.schema.json` is regenerated by `cargo xtask
   schema` and `schema-check` passes.
2. The loader refuses, with a stable code at the step's path, a prefix with no words, a blank or
   empty word, a program written as a path, and a program on `CommandPrefix::PROGRAM_RUNNERS`
   (the shells and shell evaluators, the wrappers, the script interpreters, `npx`); tests in
   `aep-driver-spec` name each refusal and hold the whole list.
3. `StepContext` carries the running step's `commands`, filled by `aep-driver` from the map for an
   `llm` step and empty for every other kind; a test in `aep-driver`'s `driving.rs` reads them
   from an executor, so a driver that handed every step an empty list fails it.
4. `driven_surface` admits one simple invocation whose leading words match a declared prefix, the
   `aep` area word skipped on both sides when a verb follows it, so `aep artifact new` matches
   `[aep, plan, artifact]` and `[aep, plan]` does not admit `aep drive run`; refuses an invocation
   matching none, naming the declared prefixes; refuses `cargo --config` and `rg --pre` under every
   surface (`RUNNER_FLAGS`); keeps refusing a composed command line and a quoted or partial
   spelling; keeps admitting the read-only programs under `repository.read`; and falls back to the
   current surface when the step declares nothing. Tests in `aep-cli` cover each case.
5. `drivers/development/checks.yaml` declares `[aep, plan, artifact]` on `receive`, `specify`,
   `decompose`, `establish_verifiers` and `adversarial_verify`, and on `implement` `task check`,
   `task fmt`, `task schema`, `task ess`, `task status` and `cargo build|check|clippy|doc|fmt|test`;
   every `llm` step's `scope:` denies `drivers/**`, `Taskfile.yml`, `.cargo/**` and
   `rust-toolchain*`; `aep govern validate --root .` loads it.
6. `website/docs/reference/documents.md` documents `commands:` beside `scope:`, states what the
   declaration does not bound (what the tree does when an admitted build runs), and `CHANGELOG.md`
   carries an Unreleased entry per user-visible change.
7. `AEP_BIN=<target>/release/aep task check` exits 0.

## Out of scope

- The native arm's program allowlist and prompt text in metaharness, which render the same decision
  there (`driven_programs`, `prompt_for`); named to that session at release.
- `drivers/development/default.yaml`, which keeps its current surface.
- A sandbox for what an admitted build does with the tree; the harness's, as the approval record's
  D6 says.
