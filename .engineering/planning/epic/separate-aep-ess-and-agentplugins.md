## Context

The current repository owns three independently meaningful products: Agentic Engineering Protocol governance and execution, Executable System Specification modeling and tooling, and harness-specific agent integrations. Their shared workspace has turned repository co-location into dependency and naming coupling. The operator accepted a coordinated split on 2026-09-01.

## Required boundaries

- Rename `engineering-protocols` to `aep`; `aep` becomes the canonical command while `protocol` remains a byte- and exit-compatible alias.
- Extract ESS to `beyond10x/ess` with no AEP or historical Engineering Protocol dependency.
- Extract curated integrations to `beyond10x/agentplugins`, marketplace id `beyond10x`, initially shipping `aep-planning`, `adp`, and `ess-schema`.
- Move the Kubernetes scanner into ESS as a credential-edge adapter and archive `infra-scout` after equivalence and redaction evidence exists.
- Keep AEP's generic planning substrate, ADP and AOP profiles, provider-backed planning, driver, trace evaluation, and governance.
- Move ESS conformance coupling behind an optional AEP-side adapter consuming a standalone ESS report; core AEP must not compile against ESS modeling types.

## IR boundary

Do not introduce a generic facet registry or `ess-ir/2`. Extend Rust-owned `EssIr` and `InfraIr` with concrete typed kinds, handles, ordered collections, and relations only when an importer or projector establishes semantics. Keep the two IRs separate until a concrete use case requires unification. Preserve compiler-minted handles, total resolved lookups, deterministic serialization, explicit source-specific typed structures, and current serialized bytes. A format version moves only when persisted meaning, identity, references, canonicalization, reader compatibility, or the envelope changes; strict v1 additive changes require an old-reader test.

## Adapter contract

`ess import <adapter>` produces validated typed IR, coverage, diagnostics, and unresolved references without guessing missing semantics. `ess project <adapter>` produces artifacts, obligations, and explicit refusals but never applies them. Each adapter declares its supported kinds and directions. Initial adapters are Kubernetes import/projection and OpenAPI import/projection. Round-trip guarantees cover only the declared subset; unsupported constructs become coverage gaps, obligations, or refusals.

## Ordered migration

1. Record an Atlas ADR naming consumers and release order; add dependency and command-equivalence guards.
2. Extract ESS with filtered history, independent primitives, stable fixtures, and stable generated bytes.
3. Import `infra-scout`, preserve secret redaction, and keep live-cluster tests outside the offline gate.
4. Extract and validate `agentplugins` with no obsolete marketplace identity.
5. Remove extracted sources, rename the original repository to `aep`, and publish canonical `aep` plus the `protocol` alias.
6. Update `aep-service`, `entity-runtime`, `metaharness`, Atlas, public documentation, and pinned fixtures in dependency order.

## Acceptance

Every affected repository passes its full gate and documentation build. ESS has no AEP/EP dependency, v1 fixtures and generated bytes remain exact, old `protocol` behavior is equivalent to the relevant new command, resolved lookups remain total and deterministic, adapter coverage and semantic round trips are explicit, Kubernetes secret-redaction mutation guards still fail, and plugin manifests contain no obsolete marketplace or mixed repository identity.
